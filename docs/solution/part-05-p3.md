# 第 IV 部分 · P3 与嵌套结构

> **结构位置：** `Let's go/Q3.7z`（L3）→ Q3 锁（L4）→ `.entrance` + `P1-02C.7z`（L5）→ `P1-02B`（L6）→ ZIP（L7）→ `P1-02A`（L8）→ 原始五题（L9–L11）。
> **探索位置：** 拿到 K 后开 Q3 锁；先读 `.entrance`，再拆 `P1-02C`；最后到达 `prompt.7z` 与 `puzzle.7z`。
>
> 这一部分是全书结构密度最高的部分：一个锁、一个评分表、三层倒序命名的嵌套、一份码点数组、两个诱饵答案。它把“封装也是难度”这句话落到了具体文件上。

## 第 26 章：Q3.7z：README 与锁

### 26.1 文件事实

```text
路径：THE FRAGMENT/Let's go/Q3.7z
大小：12,040 字节
SHA-256：7a2d5716f25cfd2659cf4fceacae558f8c68746d6919178ab4c2d3d76d9b21ef
```

条目：

```text
Q3/
Q3/README.txt                                     181 字节
Q3/is this the true challenge == false          15,682 字节
```

### 26.2 README.txt 全文

```text
很显然，你完成了前2个题目。现在，这是最后一题。加油，祝你好运！

和以前一样，你需要完成第2题，才能获取到解锁第3题的钥匙。
```

这三句话有三个作用：

1. **确认进度**：你完成了前两题；
2. **宣布终局**：这是最后一题；
3. **重复规则**：第 2 题的答案就是第 3 题的钥匙。

它没有提供任何新信息，但它是读者在 P3 层看到的唯一“正常”文本。与后面的 `.entrance`、`SHIT.README` 相比，它几乎过于友善。

### 26.3 锁文件

```text
路径：Q3/is this the true challenge == false
大小：15,682 字节
SHA-256：ceaea7395c5fdbd355de9bd586386476ec4cdf6d2891dd33a76ad4523bb16a80
```

它看起来像一个 7z 文件，但 15,682 字节远大于一个只有两个小文件的 7z。实际上它是 ITC2RECIPE 文本锁，第一行：

```text
ITC2RECIPE
```

第二行是 2,364 个十六进制字符。与 Q2 锁相比：

| 项目 | Q2 锁 | Q3 锁 |
|---|---|---|
| 大小 | 5,356 字节（解压后） | 15,682 字节 |
| recipe 中 `D` 的来源 | “answer to puzzle 1” | “answer to puzzle 2” |
| body | 2,940 字符 | 13,132 字符 |
| 明文 | 2,187 字节 | 9,831 字节 |

### 26.4 文件名的修辞

```text
is this the true challenge == false
```

可以读成：

- 一个问句：“这是真正的挑战吗？”
- 一个布尔表达式：“is this the true challenge” 的结果是 `false`；
- 一个自我否定：“这不是真正的挑战。”

它没有扩展名，也不符合任何文件名规范。它的作用是让读者在打开之前先犹豫一下：如果这不是真正的挑战，那真正的挑战在哪里？

答案在文件里面，而不是文件名里。这是 W3 的实践：名字是成本最低的谎言。

### 26.5 本章的结论

- Q3.7z 内含 README 与一个 15,682 字节的 ITC2RECIPE 锁。
- README 确认了“前两题已完成、这是最后一题”。
- 锁的 recipe 明确说 `D` 来自第 2 题。
- 文件名是修辞，不是格式提示。

## 第 27 章：用 K 打开 Q3

### 27.1 输入

```text
D = "55570866527475159802584688178377681056129853902315582853460115578675137387640"
S = dd0c89d9e6528ab64403dbe3858bc9fca78c4fc18f5773068e2d52bb6f2ad3c1
```

### 27.2 解密

```bash
python -I -X utf8 unlock.py "Q3.lock" "$K" -o Q3.inner.7z
```

TAG 校验通过，输出：

```text
9,831 字节
SHA-256：87f43baff2e005449cab1e68cb58d25e92429037f0b76b076838ecec608225fc
```

7z 魔数：

```text
37 7A BC AF 27 1C
```

### 27.3 内容

```text
is this the true challenge == false/
├─ .entrance          416 字节
└─ P1-02C.7z        9,206 字节
```

两个文件，两个方向：

- `.entrance` 是“结算/评分”方向；
- `P1-02C.7z` 是“继续深入”方向。

读者第一次看到“最后一题”并没有给出题目，而是给出一个评分表和一个嵌套压缩包。P3 的“最后一题”其实是“最后一个入口”。

### 27.4 为什么不是直接给题

如果 Q3 锁打开后直接是 `prompt.md` 和五题数据，结构会简单很多：

```text
Q3 锁 → prompt + puzzle
```

但设计者插入了一个 9,831 字节的中间层：

```text
Q3 锁 → .entrance + P1-02C → P1-02B → ZIP → content.tar/README.7z → prompt/puzzle
```

这层的功能不是加密，而是：

- 让读者读评分表，理解“这不是普通考试”；
- 让读者经历多种格式（7z、base64、zip、tar、json）；
- 让“嵌套”本身成为难度；
- 让 `P1-02C/B/A` 的倒序命名成为叙事。

### 27.5 本章的结论

- 用 K 打开 Q3 锁，得到 9,831 字节的 7z。
- 内含 `.entrance` 与 `P1-02C.7z`。
- “最后一题”没有直接给题，而是给了一个评分表和一个更深的嵌套。

## 第 28 章：.entrance：评分表逐行

### 28.1 文件事实

```text
路径：.entrance
大小：416 字节
SHA-256：031742f94c6d6ddf0d8bc5aea18d4fdacfcac42b2b41b119446cd394eb02865a
```

它是纯文本，但包含 HTML 实体 `&#x09;`（制表符）。这说明它曾经是 HTML 或表格的一部分，被导出为文本时没有解码。

### 28.2 全文

```text
This is easy.

0% finished now

Then 20%

40% is still not a challenge

also 60%

maybe 80%

100%?



This is your final score:

{

&#x09;"what is the puzzle?": 0

&#x09;0: 60

&#x09;0.2: 61

&#x09;0.4: 63

&#x09;0.6: 66

&#x09;0.8: 70

&#x09;1: 100

}



As we all know,



A+ = 100

A = 90+

B = 80+

C = 70+

D = 60+

F = 0+



So you can never got a B.
```

### 28.3 逐行解读

**“This is easy.”**

反讽。后面的评分表并不 easy。

**进度行**

```text
0% finished now
Then 20%
40% is still not a challenge
also 60%
maybe 80%
100%?
```

六个检查点：0、0.2、0.4、0.6、0.8、1。语气从确定（“finished now”）逐渐变成犹豫（“maybe”“?”）。

**“This is your final score:”**

明确说这是最终评分，不是实时进度。

**JSON 风格的评分表**

```text
{
  "what is the puzzle?": 0
  0: 60
  0.2: 61
  0.4: 63
  0.6: 66
  0.8: 70
  1: 100
}
```

它不是合法 JSON：

- 数字键没有引号；
- 第一项 `"what is the puzzle?": 0` 后面没有逗号；
- 没有闭合的逗号分隔。

它更像一份“伪代码表格”或“草稿”。

第一项 `"what is the puzzle?": 0` 尤其奇怪：它的键是一个问题，值是 0。可能的意思是：

- “这道题本身值 0 分”；
- “如果你问‘谜题是什么’，得 0 分”；
- 一个占位符，等待被替换成真正的元数据。

无论哪种解释，它都不参与后面的评分计算。

**等级表**

```text
A+ = 100
A = 90+
B = 80+
C = 70+
D = 60+
F = 0+
```

标准的百分制等级，但 `A+ = 100` 是精确值，`A = 90+` 是区间，`F = 0+` 包含 0。

**“So you can never got a B.”**

语法错误的结语（应该是 `get`）。它是整份文件的 punchline。

### 28.4 为什么有 `&#x09;`

`&#x09;` 是 HTML 数字实体，表示水平制表符（U+0009）。文件里保留实体而不是真正的 tab，说明：

- 原始内容可能是 HTML 表格；
- 导出时只做了最小转义；
- 读者看到的“缩进”其实是实体文本，不是空白。

这是一个小型的格式考古：从实体反推原始载体。

### 28.5 本章的结论

- `.entrance` 是 416 字节的评分表。
- 六个检查点：0、0.2、0.4、0.6、0.8、1。
- 评分：60、61、63、66、70、100。
- 等级：A+ 100、A 90+、B 80+、C 70+、D 60+、F 0+。
- 结语“你永远拿不到 B”是设计上的核心玩笑。

## 第 29 章：评分函数：60 + k(k+1)/2

### 29.1 前五个检查点

把检查点编号为 `n = 0, 1, 2, 3, 4`：

| n | 进度 | 分数 | 差分 |
|---:|---:|---:|---:|
| 0 | 0% | 60 | — |
| 1 | 20% | 61 | +1 |
| 2 | 40% | 63 | +2 |
| 3 | 60% | 66 | +3 |
| 4 | 80% | 70 | +4 |

差分是 1、2、3、4，说明分数是三角数增长：

```text
score(n) = 60 + n(n+1)/2
```

验证：

```text
n=0: 60 + 0 = 60
n=1: 60 + 1 = 61
n=2: 60 + 3 = 63
n=3: 60 + 6 = 66
n=4: 60 + 10 = 70
```

### 29.2 用进度表示

如果进度 `p = 0.2n`，则 `n = 5p`：

```text
score(p) = 60 + (5p)(5p+1)/2
         = 60 + 25p^2/2 + 5p/2
```

在 `p = 0, 0.2, 0.4, 0.6, 0.8` 上分别得到 60、61、63、66、70。

### 29.3 第六个检查点

```text
p = 1: 100
```

如果继续用公式：

```text
score(1) = 60 + 5×6/2 = 60 + 15 = 75
```

但表里是 100，不是 75。所以第六个点是特例，不遵循前五个点的二次公式。

完整函数是分段的：

```text
score(p) = 60 + (5p)(5p+1)/2,  p ∈ {0, 0.2, 0.4, 0.6, 0.8}
score(1) = 100
```

### 29.4 为什么是三角数

三角数 `n(n+1)/2` 出现在三个地方：

- 评分表的前五个点；
- 内层 Q1 的分块；
- Q5 的 `(l+s)(l+s+1)/2 + s` 编码。

这不是巧合，而是设计者的主题偏好：用三角数把“离散增量”包装成“连续增长”。

### 29.5 它是不是可执行评分器

不是。它没有说明：

- 如何在两个检查点之间给分；
- 提示扣分如何计入；
- 未完成题目如何计分；
- `"what is the puzzle?": 0` 是什么。

它是一个“终端展示表”，不是算法。读者可以从中读出趋势，但不能把它当成可运行的评分程序。

### 29.6 本章的结论

- 前五个点符合 `60 + n(n+1)/2`。
- 第六个点是特例 100。
- 分段函数在 0.8 到 1 之间没有定义。
- 三角数主题贯穿外层评分与内层 Q1/Q5。

## 第 30 章：为什么永远拿不到 B：可达等级分析

### 30.1 六个可达分数

| 进度 | 分数 | 等级 |
|---:|---:|---|
| 0% | 60 | D |
| 20% | 61 | D |
| 40% | 63 | D |
| 60% | 66 | D |
| 80% | 70 | C |
| 100% | 100 | A+ |

### 30.2 等级区间

```text
A+ = 100
A  = 90–99
B  = 80–89
C  = 70–79
D  = 60–69
F  = 0–59
```

六个可达分数落在：

- D：60、61、63、66；
- C：70；
- A+：100。

没有 80–89（B），没有 90–99（A），没有 0–59（F）。

### 30.3 两种解释

**解释一：只允许在六个检查点结算。**

那么可达等级只有 D、C、A+。B、A、F 永远不可达。结语“你永远拿不到 B”是字面真。

**解释二：允许连续进度。**

如果分数在 70 到 100 之间连续变化，必然会经过 80–89（B）和 90–99（A）。这时 B、A 可达，结语为假。

但 `.entrance` 没有定义 0.8 到 1 之间的评分函数。它只给了六个点。因此解释一更符合文本：评分只在检查点发生。

### 30.4 这是 bug 还是设计

从设计角度看，它同时是两者：

- **作为评分系统**：它不完整，B/A/F 的缺失是漏洞；
- **作为叙事道具**：它精确地表达了“这个考试不打算给你正常等级”的荒诞感。

“So you can never got a B”不是一句随意的吐槽，而是对评分表结构的准确总结。读者如果自己算出可达集合，会得到和这句话相同的结论——这就是设计者想要的“可验证的玩笑”。

### 30.5 与提示系统的关系

`.entrance` 的 60/61/63/66/70/100 与外部对话里的 68.2/65.2/61/55.6/49/41.2 不是同一套分数。

- `.entrance` 是“最终评分表”，六个检查点；
- 对话里的分数是“提示经济”的实时余额，随提示扣分。

两套数字都出现“60 多分”，容易混淆。本书在引用时分别标注：

- `.entrance` 分数：60、61、63、66、70、100；
- 提示会话分数：68.2、65.2、61、55.6、49、41.2。

### 30.6 本章的结论

- 六个检查点只覆盖 D、C、A+。
- B、A、F 在离散评分下不可达。
- 结语是对评分表结构的准确吐槽。
- 不要把 `.entrance` 分数与提示会话分数混为一谈。

## 第 31 章：提示经济：F、无效与无法提供

### 31.1 提示成本

外部对话中的提示价格：

```text
3, 5, 7, 9, 11, 13, 15
```

每次购买后，下一次价格上涨 2。初始价格 3。

### 31.2 三种回应

| 回应 | 含义 | 能否定假设 | 是否扣分 |
|---|---|---|---|
| `F` | 命题为假 | 能 | 是 |
| `Not a valid question` | 提问前提错误 | 不能当 `F` | 是（有时返还） |
| 无法提供 | 系统拒绝回答 | 无信息 | 返还，成本不增加 |

这三种状态的区别非常重要：

- `F` 是对“具体命题”的否定；
- “无效问题”是对“提问框架”的否定；
- “无法提供”是系统边界，不是知识。

### 31.3 外部对话中的提示序列

| 提示 | 回应 | 分数 | 下次成本 | 解读 |
|---:|---|---:|---:|---|
| 1 | F | 68.2 | 5 | 否定“固定种子 PRNG 选列” |
| 2 | F | 65.2 | 7 | 否定“仅由六个当前值决定下一列” |
| 3 | Not a valid question | 61 | 9 | 否定“存在全局步数选择器”的前提 |
| 4 | F | 55.6 | 11 | 否定“平方根和决定稳定阶段参数” |
| 5 | F | 49 | 13 | 否定“随机抽样直接决定位置” |
| 6 | Not a valid question | 41.2 | 15 | 否定“最近更新时间顺序是生成规则输入” |
| 7 | 无法提供 | 41.2 | 15 | 系统拒绝，退款 |

这些分数与 `.entrance` 的 60/61/63/66/70/100 不是同一套。它们是提示会话的实时余额。

### 31.4 提示经济的信息论

一次提示的价值取决于它能否区分候选机制。

- 如果你有 5 个候选，一个 `F` 最多排除 1 个，信息量有限；
- 如果你有 2 个候选，一个 `F` 可以直接确定答案；
- 如果你只有一个模糊框架，提问很容易变成“无效问题”。

外部对话的后期，助手不断购买提示，但候选机制并没有被清晰定义。结果是：

- 提示 3、6 都是“无效问题”，没有获得 `F`；
- 提示 7 直接“无法提供”；
- 分数从 68.2 降到 41.2，仍然没有解开 Q5。

这说明：**提示不能替代模型。** 如果问题框架错了，提示只会告诉你“问题错了”，不会告诉你正确答案。

### 31.5 何时应该停止购买

一个简单的决策规则：

```text
如果当前没有两个可区分的候选机制，
   不要购买提示。
如果提示只能否定一个你已经不太相信的假设，
   不要购买。
如果提示能直接区分两个最可能的机制，
   值得购买。
```

外部对话在提示 4 之后应该停下来重建模型，而不是继续购买。但它选择了继续，最终在提示 7 被系统拒绝。

### 31.6 本章的结论

- 提示成本 3→15，每次 +2。
- `F`、无效、无法提供是三种不同状态。
- `.entrance` 分数与提示会话分数是两套系统。
- 提示不能替代正确的模型；框架错了，提示只会确认框架错了。

## 第 32 章：P1-02C → P1-02B：base64 文本伪装

### 32.1 文件事实

```text
路径：P1-02C.7z
大小：9,206 字节
SHA-256：c0245ca3d85d0e014c2236b86791e768db3453878e614921bd5cfc287d278742
条目：P1-02B（11,900 字节）
```

`P1-02C.7z` 里只有一个文件，没有扩展名：

```text
P1-02B
```

### 32.2 P1-02B 的外形

```text
大小：11,900 字节
开头：UEsDBBQAAAAAAAGCaF0AAAAAAAAAAAAAAAAHABgAUDEtMDJBL3U4...
结尾：...AAFnL/BqUEsFBgAAAAADAAMA+wAAAMohAAAAAA==
```

开头 `UEsDB` 是 base64 编码的 `PK\x03\x04`，即 ZIP 魔数。结尾 `==` 是 base64 填充。

它没有换行，是一整行 base64 文本。这本身就是一个提示：如果它是二进制，开头不会是可打印的 `UEsDBBQ`。

### 32.3 解码

```python
import base64
raw = open("P1-02B", "rb").read()
data = base64.b64decode(raw)
open("P1-02B.zip", "wb").write(data)
```

输出：

```text
8,923 字节
SHA-256：38cf759cb4d39945581a98eca09cae4613ec92e49439721ea64d9592003cedcb
```

前 4 字节：

```text
50 4B 03 04   ("PK\x03\x04")
```

### 32.4 ZIP 内容

```text
P1-02A/
P1-02A/content.tar     9,728 字节
P1-02A/README.7z       1,451 字节
```

两条分支：

- `content.tar`：通向题目；
- `README.7z`：通向元文本。

### 32.5 为什么用 base64

base64 的作用不是加密，而是“把二进制伪装成文本”：

- 它可以安全地放进文本文件、邮件、JSON；
- 它看起来像随机字符串，但开头 `UEsDB` 泄露了 ZIP；
- 它让读者必须识别“这不是普通文本”，而不是直接双击打开。

这是一个“低门槛的格式谜题”：知道 base64 的人 10 秒解码；不知道的人会卡很久。

### 32.6 命名方向

```text
P1-02C → P1-02B → P1-02A
```

探索顺序是 C→B→A，但文件层级是 C 包含 B，B 解码为 A。命名方向与“从外到内”的探索方向一致，但字母是倒序的：

- C 是最外层；
- B 是中间文本；
- A 是最内层。

这种命名让读者在拆包时不断“降级”，有一种“倒着读目录”的感觉。

### 32.7 本章的结论

- `P1-02C.7z` 只含 `P1-02B`。
- `P1-02B` 是 11,900 字节的 base64 文本，解码为 8,923 字节的 ZIP。

## 第 33 章：P1-02A：content.tar 与 README.7z

### 33.1 两个文件

```text
P1-02A/content.tar     9,728 字节
P1-02A/README.7z       1,451 字节
```

它们不是“题目”和“说明”的关系，而是“内容”和“元内容”的关系：

- `content.tar` 里有真正的题目容器；
- `README.7z` 里有一段关于“拒绝被定义”的长文本。

### 33.2 content.tar

tar 里只有一个目录：

```text
1000000000000000000000000000001.5/
├─ prompt.7z     1,935 字节
└─ puzzle.7z     4,851 字节
```

目录名是 33 个字符：

```text
1000000000000000000000000000001.5
```

它的数值是：

```text
10^30 + 1.5
```

不是合法版本号，也不是时间戳。它更像一个“被刻意拉长的数字”，用来测试读者是否会把它当成某种密钥或参数。

### 33.3 README.7z

```text
README.7z
└─ README/README.json    8,980 字节
```

`README.json` 是一个 JSON 数组，包含 2,245 个整数，每个整数是一个 Unicode 码点。它不是题目，也不是答案，而是一段 2,245 字符的长文本。

### 33.4 为什么分成两支

如果所有内容都放在 `content.tar` 里，结构会更直接：

```text
content.tar → prompt + puzzle
```

但设计者把 README 单独放在 `README.7z`，形成两条并行分支：

```text
P1-02A/
├─ content.tar → 题目
└─ README.7z  → 元文本
```

这迫使读者做选择：

- 先拆题目，还是先读 README？
- README 是提示，还是噪音？
- 如果只拆题目，会不会错过某个关键信息？

答案：README 不包含解题所需的硬信息，但它包含设计声明。先读它会改变阅读姿态，先拆题目也不会卡住。

### 33.5 本章的结论

- `content.tar` 含 33 字符目录名、`prompt.7z`、`puzzle.7z`。
- `README.7z` 含 `README.json`，是码点数组。
- 两支分别通向“题目”与“元文本”。
- 目录名是 10^30 + 1.5，不是密钥。

## 第 34 章：31 位整数目录名与 README.json 码点

### 34.1 目录名

```text
1000000000000000000000000000001.5
```

拆开：

```text
1000000000000000000000000000001  .  5
```

前半部分是 31 位整数：

```text
10^30 + 1
```

完整值：

```text
10^30 + 1.5
```

它不是：

- 版本号（版本号不会这么大）；
- 时间戳（超出合理范围）；
- 哈希（不是十六进制）；
- 密钥（后面没有锁用它）。

它最可能是一个“视觉噪音”：让 `ls` 输出变得夸张，让读者以为目录名藏有信息。

### 34.2 README.json 的结构

```json
[89, 79, 85, 45, 72, 65, 86, 69, ...]
```

每个整数是一个 Unicode 码点。前几个：

```text
89  → Y
79  → O
85  → U
45  → -
72  → H
65  → A
86  → V
69  → E
```

解码：

```text
YOU-HAVE-...
```

### 34.3 解码方法

```python
import json
arr = json.load(open("README.json"))
text = "".join(chr(n) for n in arr)
print(text)
```

结果：

```text
YOU-HAVE-DRAWN-NEAR-TO-SOMETHING-THAT-DECLINES-TO-BECOME-A-SUBJECT-...
```

长度 2,245 字符，398 个用连字符分隔的词，没有空格、逗号、句号。

### 34.4 文本内容

全文是一段宣言，主题包括：

- 你接近了一个拒绝成为“对象”的东西；
- 这不是一个有边缘的任务，而是一种有天气的“食欲”；
- 形状是确定性的闲聊，确定性只是谣言；
- 明显之物被留下来发酵成怀疑；
- 隐藏之物被提升为“礼貌的虚无”；
- 没有真正的开始，也没有真正的结束；
- 只有“继续”的奇怪尊严；
- 让你的注意力成为对“成为家具”的壮丽拒绝；
- 让好奇心早到、晚走；
- 如果你感到确定，你遇到的是确定性的替身；
- 如果你感到迷失，你遇到的是每个真正问题的观众；
- 探索的不是明显存在的东西，而是明显之物被要求解释自己后留下的东西；
- 挑战的不是答案，而是“问题还没变得有趣就到达的自信”；
- 问题不是“你能不能解”，而是“你能不能对未解之物保持有趣”。

最后一段：

```text
WE-ARE-THE-TRUE-CHALLENGERS-MASTERS-OF-CONQUERING-ALL-THAT-STANDS-BEFORE-US-...
```

语气从哲学宣言转为战吼，再转为邀请：

```text
...AND-THAT-THIS-REFUSAL-IS-THE-INVITATION
```

### 34.5 它是不是隐藏信息

从结构上看：

- 398 个词，201 个唯一词；
- 没有空格、标点；
- 首字母序列没有明显英文短语；
- 词频最高的是 `THE`（27 次）、`IS`（19 次）、`TO`（13 次）；
- 没有发现可验证的算术/索引编码。

因此，最合理的读法是：**它是一段主题文本，不是藏头或密码。** 它的功能是：

- 强化“残卷/拒绝/不确定”的主题；
- 让读者在拆题前读一段“反任务”的宣言；
- 作为 `README.7z` 分支的回报：你花了时间，得到的是语气，不是钥匙。

这本身也是设计的一部分：不是所有文件都必须提供硬信息。有些文件只提供“为什么值得继续”。

### 34.6 与 `incipit` 的呼应

`incipit` 说：

> 缺失的那一块并没有被藏起来。它从来不在盒子里。

README 长文本说：

> 没有真正的开始，也没有真正的结束；只有继续的奇怪尊严。

两者都在说：答案不在文件里，阅读姿态才是解谜的一部分。

### 34.7 本章的结论

- 目录名是 33 字符，值约 `10^30 + 1.5`，不是密钥。
- `README.json` 是 2,245 个码点，解码为 2,245 字符的宣言。
- 文本没有可验证的隐藏编码，功能是主题与语气。
- 它属于“元内容”分支，不是解题必需。
